# Phase 2: Supabase PostgreSQL marketplace migration

Status: code and offline migration prepared. No live PostgreSQL DDL, account
linking, data import, deployment, or source database reads were performed in this
phase. The old TiDB DATABASE_URL has not been restored. The app no longer uses a
MySQL driver. Supabase is the only configured marketplace database target.

All existing Drizzle query sites were inspected, including marketplace reads,
cart actions, checkout, order updates, seller actions, admin actions, auth profile
creation, Navbar aggregates, and the database-test page. Standard joins, filters,
counts, ordering and SQL stock arithmetic require no dialect-specific rewrite.
No raw MySQL query remains in the active application.

This phase preserves COD checkout and the existing roles, permission guards,
statuses, shipping fields, price snapshots and stock rules. It adds no payment
provider, payment mode or business-status transition.

## Schema mapping

| MySQL | PostgreSQL | Compatibility decision |
| --- | --- | --- |
| `mysqlTable` | `pgTable` | Same 11 table names, including auth mapping |
| `int AUTO_INCREMENT` | `integer GENERATED BY DEFAULT AS IDENTITY` | Numeric IDs preserved; explicit historical IDs can be imported later |
| `int` foreign keys/stock/quantity | `integer` | Same signed 32-bit range; validate IDs and values before import |
| Inline `mysqlEnum` | Named `pgEnum` types | Same labels, ordering, defaults and nullability |
| `decimal(10,2)` | `numeric(10,2)` | Money stays exact in DB and remains string-valued in Drizzle |
| `timestamp` | `timestamp(3) with time zone` | JS Date values; export source timestamps as UTC instants |
| `varchar(n)` / `text` | `varchar(n)` / `text` | Same lengths/nullability; collation needs source-data review |
| UUID string in auth mapping | Native `uuid` | Reject invalid UUIDs; enforce Supabase Auth reference |
| `$returningId()` | `.returning({ id: table.id })` | Used by order/profile inserts |
| `result[0].affectedRows` | `.returning({ id: table.id })` and returned row count | Guarded deduction and cancellation still require exactly one row |
| MySQL LIKE under common case-insensitive collations | PostgreSQL ILIKE | Preserve case-insensitive product/shop search; not full collation equivalence |

Money columns are `products.price`, `orders.total_amount`, `order_items.price`,
`order_items.subtotal`, and `order_shops.subtotal`. Existing Number/toFixed(2)
application calculations are unchanged; this phase does not redesign rounding.

All created/updated/reviewed/expiry timestamps use explicit timezone-aware date
mapping. Defaults remain `now()`. There is no new auto-update trigger: existing
actions continue to set `updatedAt` explicitly. PostgreSQL `now()` is stable within
a transaction, which can differ slightly from MySQL statement-time defaults.

### Enums

| Type | Values |
| --- | --- |
| `user_role` | USER, SELLER, ADMIN |
| `user_status` | ACTIVE, SUSPENDED |
| `shop_status`, `product_status` | ACTIVE, INACTIVE |

| `order_status`, `order_shop_status` | PENDING, CONFIRMED, SHIPPED, COMPLETED, CANCELLED |

Separate order/shop and product/shop enum types keep future schema changes
independent. The current queries compare enum columns to values, not to a
different enum type. Future cross-type comparisons require casts or shared types.

ON UPDATE remains NO ACTION. Nullable snapshot references remain nullable.
Deleting a Supabase identity removes its mapping, not the local user/order
history. The migration references but does not create or alter `auth.users`.

### Uniqueness and indexes

Preserved: all primary keys; unique email, category name, session token hash,
shop owner, mapped local user; `(user_id, product_id)` cart uniqueness and
`(order_id, shop_id)` shop-order uniqueness. PostgreSQL's default distinct NULLs
preserve multiple historical shop-order rows after shops are deleted.

Added unique expression indexes on `lower(users.email)` and
`lower(categories.name)` retain case-insensitive duplicate protection. Existing
case-sensitive unique constraints are retained as well. Source collation has not
been inspected live: accent equivalence, trailing spaces, normalization and locale
sorting remain migration preflight gates, not a claim of exact MySQL equivalence.

Explicit nonunique indexes cover `cart_items.product_id`, `sessions.user_id`,
`shop_requests.user_id`, `products.shop_id`, `products.category_id`,
`orders.user_id`, all three `order_items` foreign keys and `order_shops.shop_id`.
Other FK lookups are covered by primary/unique indexes or the leftmost columns of
composite unique indexes. PostgreSQL does not implicitly index referencing FK
columns as MySQL does.

### Supabase access

RLS is enabled on all 11 public tables with no public/API policies. Browser
publishable-key clients cannot access marketplace rows directly. Authorized
marketplace operations continue through Next.js server-side Drizzle and the
existing role/ownership checks. The documented pooler `postgres.PROJECT_REF`
connection bypasses RLS; never expose its password to the browser. A future
restricted runtime DB role needs an explicit grants/policy design.

No application SQL functions, triggers, Auth user writes, Storage bucket/policy
changes or data inserts are included in the migration. Identity sequences are
created by PostgreSQL. Supabase owns the `auth` and `storage` schemas.

## Connections and dependencies

Runtime `DATABASE_URL`: in Supabase Dashboard open your project, click Connect,
select Shared Pooler and Transaction mode. Copy the exact URI shown (port 6543):

```dotenv
DATABASE_URL=postgresql://postgres.PROJECT_REF:URL_ENCODED_DATABASE_PASSWORD@EXACT_POOLER_HOST.pooler.supabase.com:6543/postgres
NEXT_PUBLIC_SUPABASE_URL=https://PROJECT_REF.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

Use the database password, not an API key. URL-encode reserved characters in it.
Use the actual pooler hostname from Connect; do not guess the region or prefix.
The database and Auth values must refer to the same Supabase project.

Postgres.js is configured with `prepare: false`, TLS certificate/hostname
verification, `max: 1`, idle timeout 20 seconds and connection timeout 10 seconds.
Runtime rejects missing URLs, MySQL URLs and non-Supabase/non-6543 pooler URLs.
There is no alternate database fallback. Client initialization is lazy, so
type-checking/building does not require or contact a live database.

For a future approved schema migration, use a separate server-only
`DATABASE_MIGRATION_URL`: direct connection port 5432 when IPv6 is available, or
Shared Pooler session mode port 5432 for an IPv4 environment. Drizzle config uses
only this optional variable for migration credentials. Neither URL was written
to `.env.local` in this phase. No migrate/push command has been run.

Retained: `drizzle-orm`, `drizzle-kit`, Supabase SSR/Auth packages. Replaced:
`mysql2` with `postgres`. Added dev-only `@electric-sql/pglite` to validate actual
PostgreSQL SQL and transactions in memory without live credentials. Legacy
MySQL scripts are archival and are no longer supported by runtime dependencies.

## SQL compatibility and release gates

- Old backtick-quoted DDL, inline enums, AUTO_INCREMENT and MySQL migration
  snapshots cannot run in PostgreSQL. `drizzle-postgres/` starts independent
  PostgreSQL history; never mix its journal with `drizzle/`.
- RETURNING replaces MySQL insert/update metadata. Stock checks still execute
  atomically in the database; a failed conditional update aborts checkout.
- PostgreSQL rejects zero/invalid dates, invalid UUIDs, out-of-range numerics,
  invalid enum labels and orphan references. Audit before import; do not silently
  coerce bad records.
- UUID mappings now require actual Auth users in the target project. Old mappings
  cannot be blindly copied to a different Supabase project.
- Collation, case/accent handling, trailing spaces and sorting require a real
  source-data audit. The local tests cover case-insensitive search/uniqueness,
  not every source-language collation behavior.
- PostgreSQL defaults to READ COMMITTED; MySQL often defaults to REPEATABLE READ.
  PostgreSQL transactions abort after statement errors. The profile race recovery
  lookup is outside the aborted transaction. Concurrent checkout/status tests
  against an approved staging pooler remain necessary before release.
- Existing seller status aggregation has duplicated logic, including different
  handling of cancelled shops than the shared helper. It is left unchanged to
  avoid bundling a business-logic change into the dialect conversion.
- Legacy session rows do not authenticate Supabase users. The sessions table is
  retained for the existing admin cleanup action; do not import active legacy
  sessions. Suspension continues to check local status, but legacy-session deletion
  does not revoke Supabase JWTs.
- Product image upload/delete still uses `public/uploads/products`. Moving this
  to Supabase Storage is a separate step required before a full Vercel cutover;
  this phase preserves `image_url` strings and does not move files or create buckets.
- A successful build is not evidence of a configured live database or completed
  migration. Current app runtime needs the approved schema plus connection values.

## Future data migration plan — separate approval required

1. Agree source/target project, maintenance window and rollback criteria. Take a
   verified source backup/export. Do not restore a source URL into application
   configuration; use a separately authorized offline export process.
2. Inventory source column types, collation/timezone, counts, role/status values,
   duplicate normalized emails/category names, invalid dates, money ranges,
   UUID mappings and orphan FKs. Resolve discrepancies through a reviewed report.
3. Rehearse schema application and import on an isolated Supabase staging project.
   Review the entire generated migration and grants before any live application.
4. Plan Auth separately: reconcile/import users using supported Auth APIs, retain
   compatible bcrypt hashes where approved, never overwrite an existing Supabase
   account just because email matches. Produce a verified numeric-ID-to-UUID map.
5. Export consistent UTC timestamps and decimal strings; retain all numeric IDs,
   snapshots, roles/statuses and null references. Import users/categories first,
   then shops/shop_requests, products, orders, order_items/order_shops and cart_items.
   Import reviewed auth mappings only after both referenced users exist. Leave
   legacy sessions empty. Do not import MySQL migration metadata.
6. Reset each integer identity sequence above its imported maximum ID (handle
   empty tables and positive-ID range explicitly). Identity sequences do not
   automatically advance when explicit IDs are imported.
7. Reconcile per-table counts, IDs, foreign keys, decimal totals, inventory,
   order snapshots and shop subtotals. Preserve historical inconsistencies in the
   review report; do not silently recompute historical orders.
8. Verify USER/SELLER/ADMIN, suspended accounts, search, cart, COD multi-shop
   checkout, rollback, stock deduction/return, cancellation and seller/customer
   status transitions under concurrency. Separately verify Storage cutover.
9. After approval and final write freeze/export, repeat the validated import,
   configure Vercel Production/Preview with isolated project values, rebuild,
   deploy and monitor. Keep source backups offline. This phase does not authorize
   deployment, deletion of old data, or a fallback to TiDB.

## Local verification

Verified on 2026-09-17: `npx tsc --noEmit`, `npm run build`, and `npm run lint`
passed. The auth/PostgreSQL test run passed all 23 reported tests, including
multi-shop checkout, partial cancellation and a late stock-update rollback.
The build ran without DATABASE_URL and made no live database connection.

```sh
npx drizzle-kit generate --name=supabase_marketplace
npx tsc --noEmit
npm run build
node --test tests/auth-phase1.test.cjs tests/postgres-phase2.test.cjs
npm run lint
```

Generate creates local files only. The PGlite tests apply the migration to a new
in-memory PostgreSQL instance with a minimal test-only `auth.users` fixture, then
execute real Drizzle queries and application actions. No live credentials, data,
email delivery or Supabase network services are used. PGlite cannot validate
Supavisor networking, TLS, live Auth/Storage integration or multi-connection races.
